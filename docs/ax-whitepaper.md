# AX project version 0.11

## 1. 문서의 목적

이 문서는 **기술 백서** 이다.

목적은 세 가지다.

1. 홈즈 AX 구조의 기준 아키텍처를 정의한다.
2. `Mycroft / 시스템 / agent / sub-agent`의 경계를 명확히 한다.
3. agent별 상세 기획을 작성할 때 따라야 할 공통 양식을 제공한다.

## 2. 핵심 방향

### 한 줄 정의

**새로 설계하되, 기존의 것을 재료로 삼는다.**

홈즈 AX는 기존 조직도나 현재 업무 흐름을 그대로 자동화하는 프로젝트가 아니다. 먼저 회사를 다시 설계한다는 관점에서 업무 구조를 정의하고, 기존 운영 방식·정책·데이터·문서·회의 기록을 그 구조 안에 재배치한다.

### 자동화와의 차이

- 자동화는 이미 정해진 업무를 더 빠르게 수행하는 것이다.
- AX는 업무를 수행할 수 있는 역할, 기준, 입력, 판단 경계, 결과물을 먼저 정의하는 것이다.
- 따라서 본 프로젝트의 핵심 산출물은 단순 자동화 목록이 아니라 **업무를 agent가 수행 가능한 구조로 재정의한 설계도**다.

### 설계 원칙

- 기존 업무를 그대로 복제하지 않는다.
- 기존 데이터와 운영 경험은 폐기하지 않고 입력 재료로 삼는다.
- 사람의 판단이 필요한 지점과 agent가 수행할 수 있는 지점을 분리한다.
- 각 agent는 독립 기능이 아니라 Mycroft와 L1 시스템 위에서 작동하는 역할 단위로 정의한다.

## 3. 기준 아키텍처

홈즈 AX 구조는 아래 4개 레이어로 정의한다.

```text
L0 Mycroft
  -> 회사 전체 두뇌이자 공통 운영 기반

L1 시스템
  -> 투자개발 / 상품기획 / 마케팅 / 운영 / 중개 / 사내 경영지원

L2 Agents
  -> 각 시스템 안의 대표 업무 역할

L3 Sub-agents
  -> agent를 실제 실행 가능한 세부 업무 단위로 분해한 역할
```

### L0. Mycroft

Mycroft는 회사 전체 두뇌 역할을 하는 공통 기반이다.

담당 범위:

- 데이터 연결과 정합성 관리
- 문서, 회의록, Slack, 운영 데이터의 검색/참조 기반 제공
- agent가 사용할 공통 컨텍스트 제공
- agent 실행 로그, 결과물, 피드백의 누적
- 시스템 간 중복 정의와 충돌 감지

Mycroft는 단순 데이터 저장소가 아니다. 각 시스템과 agent가 같은 기준을 보고 일하도록 만드는 공통 운영 기반이다.

### L1. 시스템

L1은 홈즈 업무를 큰 시스템 단위로 나눈 레이어다.

현재 기준 L1은 두 묶음으로 나눠 본다.

- 부동산업 관련 시스템: `투자개발 -> 상품기획 -> 마케팅 -> 운영`
- 지원 시스템: `중개`, `사내 경영지원`

| 도메인 | 참고 코드 | 핵심 역할 |
|---|---|---|
| 투자개발 | IMS | 딜 소싱, 검토, 조율, 구조화 |
| 상품기획 | PPS | 상품 구조, 가격·계약 조건, 운영 패키지 |
| 마케팅 | CMS | 고객군, 채널, 콘텐츠, 전환 성과 |
| 운영 | PMS | 자산 운영, 입주민, 재고, 계약, 시설 |
| 중개 | BMS | 중개부문, MR.HOMES, 계약 성사 지원 |
| 사내 경영지원 | HMS | 회의, 지식, 권한, 내부 운영 |

### L2. Agents

L2는 각 시스템 안의 대표 역할을 agent로 정의한 레이어다.

예:

- 투자개발의 검토 agent
- 투자개발의 딜 소싱 agent
- 상품기획의 공간 구성·면적 관리 agent
- 마케팅의 성과 측정 agent
- 운영의 리드 관리 agent
- 중개의 계약 agent
- 사내 경영지원의 회의 agent

### L3. Sub-agents

L3는 L2 agent를 실제 실행 가능한 세부 업무 단위로 나눈 레이어다.

예:

- 조율 agent 안의 투자자 보고 sub-agent
- 고객군·채널 관리 agent 안의 채널 우선순위 판단 sub-agent
- 광고·콘텐츠 운영 agent 안의 콘텐츠 주제 관리 sub-agent
- 계약 agent 안의 특약 검토 sub-agent

L3는 구현 단위에 가장 가깝다. 다만 L3부터 만들면 기능 목록이 흩어지기 쉽기 때문에, 항상 L1 시스템과 L2 agent 경계가 먼저 정의되어야 한다.

### 투자개발

참고 코드: `IMS`

투자개발은 투자개발본부 업무를 다루는 시스템이다. 기존 AMS는 별도 독립 시스템이 아니라 투자개발 하위의 자산 발굴·검토 기능으로 흡수한다.

```text
소싱 -> 검토 -> 조율 -> 구조화
```

주요 L2 agent:

| Agent | 역할 | L3 후보 |
|---|---|---|
| 딜 소싱 agent | 유입 매물 수집, 정리, 1차 후보화 | 채널별 수집, 비정형 매물 정리, 중복 후보 병합 |
| 검토 agent | 사업성 검토 질문에 답하고 근거를 정리 | 개략 검토, valuation, 리스크 신호, 중단 사유 정형화 |
| 조율 agent | 투자자·매도인·내부 조율 자료 준비 | 투자자 보고, 공유자료 패키징, 일정/증빙 체크 |
| 구조화 agent | Deal 구조와 Plan A/B/C 비교 | 플랜 비교, 전환 신호 감지, 구조별 체크리스트 |

### 상품기획

참고 코드: `PPS`

상품기획은 홈즈의 표준 상품 기준을 기반으로 프로젝트별 입지, 수요, 건물 조건, 사업비에 맞는 공간 구성과 사양을 설계하는 시스템이다. 확인된 사업 조건을 공간 상품 기준, 면적 구성, 법규·인허가 제약, 상품 전환 사업비 계획으로 구체화한다.

주요 L2 agent:

| Agent | 역할 | L3 후보 |
|---|---|---|
| 상품 표준·브랜드 관리 agent | 홈즈 공간 상품의 표준과 브랜드 정체성 관리 | 상품 표준 정리, 프로젝트별 조정 기준, 브랜드·디자인 기준, 기획안 정리 |
| 공간 구성·면적 관리 agent | 상품 표준을 실제 건물 조건에 맞는 조닝·면적 계획으로 구체화 | 층별 조닝, 유닛 타입 구성, 공용부 프로그램, 법규·인허가 제약 검토 |
| 상품 전환·사업비 관리 agent | 자산을 홈즈 상품으로 전환하는 변경 범위와 사업비 검토 | 전환 범위 판단, 마감재·FF&E 사양, 전환 사업비 산출, 비용 영향 판단 |

### 마케팅

참고 코드: `CMS`

마케팅은 잠재 고객군을 정의하고 광고, 콘텐츠, 검색, SNS, 제휴·기관 등 주요 채널을 통해 고객 반응과 문의를 만드는 시스템이다. 최종적으로 계약 또는 입주 완료 고객 1명을 획득하는 데 필요한 비용과 전환 흐름을 관리한다.

주요 L2 agent:

| Agent | 역할 | L3 후보 |
|---|---|---|
| 고객군·채널 관리 agent | 고객군, 상품, 지역, 유입 경로 연결 | 고객군 분류, 상품·지역 매칭, 채널 우선순위 판단, 유입 경로 활용 판단 |
| 광고·콘텐츠 운영 agent | 광고와 콘텐츠 채널 운영, 고객군별 메시지 관리 | 광고 캠페인 운영, 콘텐츠 주제 관리, 채널별 메시지 조정, 예산 배분 판단 |
| 반응·리드 전환 agent | 채널 반응과 문의를 운영 파트로 넘길 유효 리드로 전환 | 반응 분류, 관심도 판단, 전환 흐름 점검, 리드 전달 |
| 성과 측정 agent | 마케팅 비용과 전환 데이터를 연결해 획득 비용과 효율 측정 | 비용 집계, 전환 흐름 측정, 채널 성과 비교, 획득 비용 판단 |

### 운영

참고 코드: `PMS`

운영은 잠재 고객 문의가 접수된 이후부터 재고 확인, 계약, 입주, 거주 경험, 시설 관리까지 이어지는 운영 흐름을 다루는 시스템이다.

운영 데이터는 장기적으로 투자개발과 중개의 판단 정밀도를 높이는 입력원이 된다.

주요 L2 agent:

| Agent | 역할 | L3 후보 |
|---|---|---|
| 리드 관리 agent | 잠재 고객 문의를 상담·투어·계약 후보 리드로 전환 관리 | 문의 접수, 수요 조건 추출, 리드 상태 판단, 투어·상담 전환 |
| 재고 관리 agent | 추천·예약·계약 가능한 공간 단위 재고 관리 | 가용 공간 조회, 입주 가능성 판단, 공간 추천, 재고 상태 관리 |
| 계약 관리 agent | 예약 확정 이후 계약·입주 준비·청구·수납·변경 흐름 관리 | 계약 조건 관리, 계약 문서 처리, 청구·수납 관리, 계약 변경·연장·종료 관리 |
| 거주 경험 관리 agent | 입주 이후 요청·민원·만족도·재계약 신호 관리 | 입주민 문의, 요청·민원 조율, 생활 안내·경험 커뮤니케이션, 만족도·재계약 신호 감지 |
| 시설 관리 agent | 시설 이슈 대응과 예방 유지보수, 운영 안정성 관리 | 시설 이슈 분류, 유지보수 조율, 작업 상태 추적, 운영 리스크 반영 |

### 중개

참고 코드: `BMS`

중개는 중개업을 다루는 시스템으로 중개사를 돕고 더 많은 계약을 체결할 수 있도록 지원하는 것이 본질이다.

중개의 핵심 업무는 `광고 -> 접수 -> 상담(자료 준비) -> 계약 -> 사후관리(CRM)`의 시간순 workflow를 따른다. 다만, 투자개발처럼 단일 파이프라인으로 끝나지 않고 본부 관제나 가맹점 지원 같은 병렬 지원 task가 함께 섞여 있다는 점이 특징이다.

주요 L2 agent:

| Agent | 역할 | L3 후보 |
|---|---|---|
| 광고 agent | 채널별 광고 운영과 성과 반영 | 채널 최적화, 이미지 정리, 성과 feedback |
| 접수 agent | 다채널 문의 접수와 배정 | 통화/채널톡/카카오/메일 통합, 진성도 scoring, 매칭 |
| 자료 준비 agent | 매물·상담·법률·규제 자료 준비 | 매물 검색, 상담자료 정리, 법률 가드레일, macro 참고 |
| 계약 agent | 계약 단계 관리와 리스크 점검 | 단계 tracking, 법정 의무 reminder, 특약 risk scoring, OCR |
| CRM agent | 고객 lifecycle 관리 | 신호 분류, persona dataset, 재접촉 시점 예측 |
| 가맹점 지원 agent | 가맹점 운영 지원 | 온보딩, 실패 통화 패턴, best practice 공유 |
| 본부 운영 agent | 본부 관제와 정책 준수 | 퍼포먼스 대시보드, 이상 거래 탐지, 브랜드 risk |

### 사내 경영지원

참고 코드: `HMS`

사내 경영지원은 사내 운영과 지식 관리를 담당한다.

주요 L2 agent:

| Agent | 역할 | L3 후보 |
|---|---|---|
| 회의 agent | 회의록, 액션 아이템, 리마인더 관리 | 회의 요약, 액션 추출, 후속 알림 |
| 챗봇 agent | 사내 지식 Q&A | 문서 검색, 담당자 찾기, 정책 질의응답 |

## 5. Agent 상세 문서 작성 기준

각 agent 상세 문서는 같은 기준으로 정리한다. 핵심은 "무슨 업무를 맡는가"보다 한 단계 더 들어가서, 어떤 상태를 판단하고 어떤 결과물을 만들어 다음 단계로 넘기는지까지 명확히 쓰는 것이다.

- 목적: 이 agent가 전체 업무 흐름에서 책임지는 구간을 한 문단으로 정의한다.
- 역할: 반복적으로 수행하는 주요 업무를 실제 담당 책임 중심으로 정리한다.
- 주요 판단: 사람 대신 또는 사람을 보조해 판단해야 하는 기준을 적는다.
- 주요 출력: 다음 단계에서 바로 쓸 수 있는 상태값, 추천 액션, 검토 결과물, 조율 필요 사항을 적는다.
- 서브에이전트: 상위 agent 안에서 필요한 핵심 처리 기능을 3-4개 정도의 실제 업무 단위로 나눈다.

## 6. 구현

### 인스턴스별 구현 소요 추정

구현 단위는 L2 agent이다. 각 agent의 난이도와 예상 소요 시간을 추정하고, L1 도메인별로 소계를 집계한다.

난이도 기준: `S` 단순 보조 기능 / `M` 단일 workflow 또는 단일 데이터 흐름 / `L` 복수 데이터·도메인 판단 포함 / `XL` 전사 공통 기반 또는 cross-system orchestration

#### 투자개발

| L2 Agent | 난이도 | 예상 소요 | 비고 |
|---|---|---|---|

### 6개월 목표

6개월 목표:

- 주요 L1 도메인 경계가 합의되어 있다.
- 우선순위 높은 L2 agent가 실제 업무에 연결되어 있다.
- 일부 L3 sub-agent가 작동 가능한 수준으로 구현되어 있다.
- 사람이 최종 판단하는 구조와 agent가 보조하는 구조가 분리되어 있다.
- 결과물과 피드백이 다시 Mycroft에 쌓인다.

## 7. 산출물

AX project의 최종 산출물은 단순 자동화 목록이 아니라, 회사의 판단 기준과 agent 실행 결과를 경영 의사결정으로 연결하는 구조다.

핵심 산출물:

| 산출물 | 설명 | 판단 기준 |
|---|---|---|
| 레이어 제로 | 전사 정책·룰·컨텍스트를 도메인별로 정리한 단일 지식 기반 | 헌법, 룰북, 컨텍스트가 분리되어 있는가 |
| C레벨 대시보드 | agent와 sub-agent 결과를 경영진이 볼 수 있는 상태값과 한 문장으로 집약 | 대표/경영진이 IR·보고·의사결정에 쓸 수 있는가 |

레이어 제로는 추상 지식베이스를 먼저 만들고 끝내는 것이 아니라, 실제 우선순위 L2 agent를 구현하는 과정에서 함께 채워야 한다. 처음 1-2개 agent가 완성될 때 해당 agent가 사용하는 정책, 예외, 금지 기준, 참고 맥락도 함께 구조화되어야 한다.

## 8. 구축 방식

구축 방식은 `사람이 룰을 제공하고, AI가 수집·정리·구현·검증을 반복하는 구조`로 본다.

역할 구분:

| 구분 | 하는 일 |
|---|---|
| 사람 | 현업 룰·정책 답변, 문서·대화 자료 제공, 코어밸류와 폐기 기준 판단, 검증 과정의 최종 확인 |
| AI/Luke | QA 시트 설계, 수집 자동화, 공백 탐지, 재질문, 룰북화, agent/sub-agent 구축, 검증·튜닝·프레임워크화 |

데이터 수집은 단순 설문이 아니다.

- 첫 질문은 유도 없이 열어 던진다.
- 답변이 오면 공백, 모순, 누락된 판단 기준을 찾아 2차·3차로 다시 묻는다.
- 같은 질문을 표현을 바꿔 다시 물어 동조편향과 방어적 답변을 줄인다.
- Slack, 카카오톡, 문서, 회의록 같은 실제 업무 데이터를 함께 보며 말과 데이터의 불일치를 확인한다.
- 결과는 `헌법 / 룰북 / 컨텍스트`로 분류해 레이어 제로에 쌓는다.

## 9. 일정 관점

일정은 `QA 수집 -> agent 개발 -> 검증·튜닝`의 세 구간으로 본다.

| 단계 | 성격 | 일정 영향 |
|---|---|---|
| QA 수집 + 크롤링 | 현업·리더십 협조 의존 | 길어질 수 있음 |
| agent 개발 | Luke/AX팀 통제 영역 | 비교적 예측 가능 |
| 검증 + 미세 튜닝 | 회사 기준에 맞추는 과정 | 검증은 빠르지만 튜닝은 오래 걸릴 수 있음 |

정확한 종료일을 먼저 못 박기보다, 일정을 앞당기는 조건을 관리하는 것이 더 정직하다.

일정을 앞당기는 조건:

- 현업 자료를 주 단위로 제공한다.
- 자료 요청과 QA에 적극 참여한다.
- 코어밸류, 금지 기준, 폐기 가능한 기준을 빠르게 판단한다.
- 첫 1-2개 agent에서 프레임워크화까지 완료해 3번째 이후 agent 적용 속도를 높인다.

## 12. 유지 가능성

이 구조가 6개월 뒤에도 유지되려면 홈즈 내부의 지속 가능성이 중요하다.

내부 지속 가능성의 근거:

- 이미 홈즈 안에는 운영 데이터, 검토 이력, 회의록, Slack, Notion, 문서 자산이 축적되고 있다.
- AX팀은 자동 회의록, 액션 추적, 리마인더, 검색/정리 보조 같은 작은 시드를 이미 운영해봤다.
- agent는 별도 세계를 새로 만드는 것이 아니라, 기존 업무 자산을 Mycroft와 L1 도메인 구조 안에 연결하는 방식으로 붙는다.

유지 가능성의 핵심:

- 사람이 전부 수기로 관리하는 두 번째 뇌를 만들지 않는다.
- agent가 만들고 사람이 검토한 결과가 다시 시스템에 남아야 한다.
- 각 agent는 산출물뿐 아니라 로그, 실패 사례, 수정 피드백을 남겨야 한다.
