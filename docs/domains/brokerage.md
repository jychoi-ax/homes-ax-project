# 중개본부 AX화 v0.1

## 1. 배경 및 목적

**본질**: MR.HOMES의 본질은 프랜차이즈형 부동산 중개 네트워크.

**가설**: 본사의 핵심 책무는 "중개사를 돕는 것"이다. 여기서 '돕는다'는 중개사가 더 많은 부동산 중개 계약을 성사시킬 수 있도록 지원함을 의미한다.

본 문서는 "중개사가 더 많은 계약을 성사시키려면 무엇이 필요한가"를 기준으로, 중개본부에 AX/AI를 적용할 수 있는 영역을 정리한 v0.1 검토안이다.

## 2. 적용 범위 개요

| 구분 | 영역 |
|---|---|
| 운영 영역 | (1) 자료 준비 (2) 계약 (3) 접수 (4) 광고 (5) 고객(CRM) (6) 가맹점 지원 (7) 본부 운영 |
| 공통 레이어 | 데이터 / 온톨로지 / 오케스트레이션 / 평가 / 거버넌스 / 개인정보 |

## 3. 운영 영역

### 3.1 자료 준비

#### (1) 맞춤 매물 검색 Agent

자료의 본질은 '매물'이며, 조건에 맞는 매물을 조회해주는 agent가 필요하다. 기능적으로는 text2SQL을 수행하는 형태로, 자연어 질의가 모호한 경우 후속 질문을 통해 사용자의 의도를 구조화·구체화한 뒤 검색을 실행한다(g-stack 방식 차용).

다만 후속 질문이 과다하면 중개사 사용성이 저하된다. 따라서 2-phase 구조를 권장한다.

- 1단계: 기본 3개 슬롯(지역·예산·매매유형)만 충족되면 일차 검색 실행
- 2단계: 결과를 보면서 조건을 narrow down

모든 슬롯을 사전에 채우려는 시도는 지양한다.

#### (2) 상담 자료 카테고리 및 수집·관리 Agent

상담 자료는 4개 카테고리로 분류된다.

- **물리**: 입지(교통, 학군, amenity) + 매물(시세 데이터)
- **법률**: 텍스트 기반. 최신성·근거가 핵심
- **규제·정책**: 텍스트 기반. 최신성·근거가 핵심
- **macro**: 매입/매각 시나리오별 시뮬레이션. 설명 가능한 모델링이 핵심

위 자료를 데이터 파이프라인으로 자동 수집·최신화·정합성 관리하는 agent가 있다면 전처리 및 데이터 품질을 안정적으로 유지할 수 있다.

#### (3) 법률·규제·정책 영역 — OAG 접근

법률 영역은 0.1%의 할루시네이션도 치명적이므로, RAG보다는 **OAG(Ontology Augmented Generation)** 접근이 더 안전하다. GitHub에 공개된 법령 데이터(대한민국 공식 운영: https://github.com/legalize-kr/legalize-kr )와 온톨로지의 관계성을 활용한다.

안전한 운영을 위해 다음 최소 가드레일을 강제한다.

| 가드레일 | 내용 |
|---|---|
| (1) 근거 인용 강제 | 조문/판례 링크 + 핵심 근거문장 |
| (2) Fallback | 근거 부족 시 '확답 불가' 응답 |
| (3) 사람 검수 layer | 출력 검수 |
| (4) UI 노출 룰 | 근거(조문/판례 URL)가 없으면 답변을 UI에서 숨기거나 "추가 확인 필요"로만 노출 |

#### (4) macro 시나리오 시뮬레이션 Agent

매입/매각 시나리오를 시뮬레이션하는 agent의 효용이 크다. 처리 구조는 (a) LLM이 시나리오 가정을 생성 → (b) 결정론적 재무 모델이 계산 → (c) LLM이 결과를 해석하는 흐름.

LLM이 생성한 시나리오의 현실성 검증 가드:

- **Backtest**: 과거 5년 데이터에 시뮬레이션을 적용하여 실제와의 근사도 측정
- **Constraint**: 한국 부동산 macro 변수의 historical range를 벗어나는 시나리오는 reject
- **Expert calibration**: 분기 단위로 전문가가 시나리오 셋을 검토

### 3.2 계약

계약서의 생성·작성은 사람이 담당하되, 관리(알림 의무, 망각 방지 등)는 AI agent가 보조한다.

- **단계별 tracking (대상: 중개사)**: 가계약 → 본계약 → 중도금 → 잔금 → 등기 → 입주 각 단계의 deadline 및 의무 자동 관리
- **법정 의무 자동 reminder (대상: 중개사)**: 실거래 신고(30일), 임대차 신고(보증금 6천만 원 / 월세 30만 원 이상), 전입신고. 누락 시 과태료 발생
- **특약 risk scoring (대상: 중개사)**: 과거 분쟁 사례 DB와 매칭하여 위험 특약 사전 경고
- **계약서 OCR 및 핵심 일자/금액 자동 추출**: 사람이 작성한 계약서를 시스템에 자동 적재

계약서 생성·작성은 별도 웹 앱 형태로 제공될 예정이므로 OCR은 후순위이며, structured data가 처음부터 확보된다. 다만 다음 경우는 OCR이 필요하다.

- 가맹 전 중개사가 보유한 legacy 계약서 import
- 상대방(매도인/임대인)이 가져오는 외부 계약서 검토
- 종이로 진행된 가계약서 사진 업로드

특약 risk scoring은 데이터 부트스트래핑이 과제. 분쟁 사례 DB가 초기에 비어 있으므로 3단계의 점진적 구조로 시작한다.

1. 공개 판례 DB(대법원 종합법률정보) 활용
2. 표준 권고 특약 vs 비표준 특약의 단순 diff
3. 운영하면서 자체 누적

### 3.3 접수

다채널(통화, 채널톡, 카카오, 메일 등)로 들어오는 접수를 한 곳에 통합 저장·전처리·할당하는 agent를 둔다.

- 통화: STT를 통해 텍스트로 변환 후 저장
- 채널톡 / 카카오 / 메일: 텍스트로 자동 저장
- 통합 저장 → 전처리(agent) → upload & noti → 할당

부가 기능:

- **진성도 scoring**: 단순 문의 vs 진성 고객을 분류하여 후속 follow-up 우선순위 결정
- **즉시 매물 매칭**: 접수와 동시에 후보 매물 3~5건을 담당자에게 push
- **할당 로직**: 지역 전문도, 현재 workload, 과거 해당 유형 성사율을 기반으로 단순 순번이 아닌 성공 확률 기반 할당
- **회신 누락 감지**: 접수 후 N시간 내 follow-up이 없으면 reminder

통화 녹음은 개인정보보호법상 사전 고지·동의가 필요하다. ARS 시작부에서 "본 통화는 녹음됩니다" 안내 및 고객 측 명시를 시스템 설계 단계에 반영. 채널톡/카카오/메일은 이미 기록 매체이므로 동의 이슈가 상대적으로 작다.

### 3.4 광고

사용자가 LLM prompt를 입력하면 DB 검색이 수행되고, OAG 기반 agent가 작성을 수행하여 사람에게 검토를 요청한다. 승인 후 agent가 업로드를 진행한다.

부가 사항:

- **채널별 최적화**: 네이버 블로그를 비롯한 채널별 노출 알고리즘 및 키워드 룰을 파악하여 generate
- **성과 피드백 루프**: 어떤 카피·사진이 클릭률·문의 전환률이 높았는지 학습하여 후속 카피에 반영
- **이미지 처리**:
  - 사진 자동 enhancement(생성 사진은 금지 — 신뢰도 저하 우려)
  - 핵심 특징 자동 태깅(향, 면적 등)
  - 잡동사니 제거 사진의 반응이 좋으면 제거 사진만 활용, 또는 정리된 잡동사니 포함 이미지로 진행하는 방향 모두 검토 가능

### 3.5 고객 (CRM)

고객 lifecycle을 고려한 CRM agent. 거래 당시 상황을 기록하고, 계약 만료 시점과 이후 진행 계획을 사전에 시나리오로 작성·시뮬레이션하여 다음 step을 준비한다. Persona 데이터셋은 부동산 중개 original data를 기반으로 자체 생성한다(Nemotron Persona Korea와 유사한 방식). 일단 생성 후 실제 데이터를 입력하여 정합성과 정교화를 지속 반복·강화한다(fine-tune 가능성이라는 장점이 있다).

핵심 기능은 lifecycle 시점을 예측하여 먼저 연락하는 agent. 한 번의 거래로 끝이 아니라 이사·투자·자녀·독립 등의 trigger가 다시 발생하므로 이를 사전 감지·예측하여 stand-by한다.

Lifecycle trigger는 실현 가능성에 따라 분리한다.

| 신호 강도 | 예시 | 비고 |
|---|---|---|
| High | 전세계약 만료 N개월 전, 자녀 학령기 진입(거래 시 기록된 자녀 나이로 추정), 대출 만기(정보 보유 시) | 내부 데이터로 추정 가능 |
| Mid | 직장 이동 | SNS 모니터링은 위험. 동의 기반 알림 옵션이 안전 |
| Low / 불가 | 출산, 이혼, 이직 의사 | 외부 신호로 잡기 어렵고, 잡을 경우 윤리 이슈 |

### 3.6 가맹점 지원

신규 중개사 온보딩 agent. 실패한 상담 통화의 패턴을 분석하여 교육 피드백을 제공하고, best practice를 자동 공유한다.

### 3.7 본부 운영

가맹점 퍼포먼스 대시보드, 이상 거래 탐지, 시장 트렌드 인사이트 전파를 담당하는 agent.

추가로 **"정책·규정 준수 모니터링"** 권장. 가맹점 수가 늘어날수록 한 가맹점의 위반이 브랜드 리스크로 확산되므로, 허위매물·표시광고법·중개수수료 상한 위반 등을 거래 데이터에서 자동 탐지하는 agent가 필요하다.

## 4. 공통 레이어

7개 agent가 silo화되지 않도록 중앙에서 잡아주는 ontology layer가 필요하며, 이는 TypeQL로 TypeDB 위에 설계 중이다.

### 4.1 데이터 Layer 분리 설계

TypeDB ontology layer만으로는 운영이 어려우며, 통상 4겹의 데이터 layer 분리가 필요하다.

| Layer | 용도 |
|---|---|
| Operational DB | 매물·고객·계약 (Postgres 등 OLTP) |
| Time-series | 시세·통화·광고 성과 (별도 store) |
| Document store | 계약서·자료·사진 |
| TypeDB | 관계·법령·규제·도메인 knowledge (semantic layer) |

### 4.2 Agent Orchestration 및 Cost Guard

Agent가 7개일 경우 사용자의 단일 요청이 다수 agent를 호출하는 일이 흔해지며, LLM API cost가 복리로 증가한다. 사전 결정 항목:

- Orchestrator 패턴 (단일 supervisor / swarm / graph 등)
- 각 agent의 model 선택 (분류·추출 등은 small model로 충분)
- Cost 모니터링 및 cap

### 4.3 Evaluation Harness

각 agent의 quality 측정 체계가 부재하면 prompt 변경의 효과를 판단할 수 없다. 평가 지표 예시:

- 매물 검색: 추천 매물의 계약 전환률
- OAG: 답변 정확도(전문가 review set)
- 진성도 scoring: 실제 계약 vs 예측의 confusion matrix
- 광고 generate: CTR, 문의 수

평가 데이터셋은 시스템 구축과 동시에 준비해야 한다.

### 4.4 책임·거버넌스 원칙

AI 매칭 오류로 인한 거래 무산, OAG 오답으로 인한 분쟁 등의 책임 소재가 모호하면 가맹점이 시스템을 사용하지 않는다. 사전 명시 원칙:

- AI는 의사결정 보조이며, 최종 판단은 중개사
- AI 출력에는 confidence와 근거를 항상 표시
- High-stakes action(광고 게재, 법률 답변)은 human-in-the-loop 필수
- AI 결정 로그를 보존(분쟁 시 추적 가능)

### 4.5 개인정보·신용정보 처리

통화 녹음, 고객 정보, 거래 정보는 모두 민감 데이터에 해당한다. 동의·보관 기한·접근 권한·삭제 권리·해외 LLM 전송 이슈를 시작 단계에 설계한다. 특히 OpenAI/Anthropic API로 통화 내용을 전송하는 것의 법적 적합성을 사전 검토(현 시점에서는 K-ISMS 인증을 받은 클라우드 안에서 처리하는 접근이 안전한 stance).

### 4.6 Ontology 거버넌스

TypeDB schema의 정의·수정·검증 주체가 long-term quality를 좌우한다.

- 법령 개정 시 schema update 책임 주체
- 신규 entity/relation 추가 절차
- Schema versioning 관리 방식

이 거버넌스 체계가 부재하면 ontology 자체가 stale해진다.
