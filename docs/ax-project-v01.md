# AX project version 0.11

## 1. 문서의 목적

이 문서는 **기술 백서** 이다.

목적은 세 가지다.

1. 홈즈 AX 구조의 기준 아키텍처를 정의한다.
2. `Mycroft / System / Agent / Sub-agent`의 경계를 명확히 한다.
3. agent별 상세 기획을 작성할 때 따라야 할 공통 양식을 제공한다.

## 2. 핵심 방향

### 한 줄 정의

**새로 설계하되, 기존의 것을 재료로 삼는다.**

홈즈 AX는 기존 조직도나 현재 업무 흐름을 그대로 자동화하는 프로젝트가 아니다. 먼저 회사를 다시 설계한다는 관점에서 업무 구조를 정의하고, 기존 운영 방식·정책·데이터·문서·회의 기록을 그 구조 안에 재배치한다.

### 자동화와의 차이

- 자동화는 이미 정해진 업무를 더 빠르게 수행하는 것이다.
- AX는 업무를 수행할 수 있는 역할, 기준, 입력, 판단 경계, 결과물을 먼저 정의하는 것이다.
- 따라서 본 프로젝트의 핵심 산출물은 단순 자동화 목록이 아니라 **업무를 agent가 수행 가능한 구조로 재정의한 설계도**다.

### 설계 원칙

- 기존 업무를 그대로 복제하지 않는다.
- 기존 데이터와 운영 경험은 폐기하지 않고 입력 재료로 삼는다.
- 사람의 판단이 필요한 지점과 agent가 수행할 수 있는 지점을 분리한다.
- 각 agent는 독립 기능이 아니라 Mycroft와 L1 system 위에서 작동하는 역할 단위로 정의한다.

## 3. 기준 아키텍처

홈즈 AX 구조는 아래 4개 레이어로 정의한다.

```text
L0 Mycroft
  -> 회사 전체 두뇌이자 공통 운영 기반

L1 Systems
  -> BMS / IMS / PMS / PPS / CMS / HMS

L2 Agents
  -> 각 system 안의 대표 업무 역할

L3 Sub-agents
  -> agent를 실제 실행 가능한 세부 업무 단위로 분해한 역할
```

### L0. Mycroft

Mycroft는 회사 전체 두뇌 역할을 하는 공통 기반이다.

담당 범위:

- 데이터 연결과 정합성 관리
- 문서, 회의록, Slack, 운영 데이터의 검색/참조 기반 제공
- agent가 사용할 공통 컨텍스트 제공
- agent 실행 로그, 결과물, 피드백의 누적
- 시스템 간 중복 정의와 충돌 감지

Mycroft는 단순 데이터 저장소가 아니다. 각 system과 agent가 같은 기준을 보고 일하도록 만드는 공통 운영 기반이다.

### L1. Systems

L1은 홈즈 업무를 큰 시스템 단위로 나눈 레이어다.

현재 기준 L1 system:

| System | 이름 | 핵심 역할 |
|---|---|---|
| BMS | Brokerage Management System | 중개부문, MR.HOMES, 계약 성사 지원 |
| IMS | Investment Management System | 투자개발, 딜 소싱, 검토, 조율, 구조화 |
| PMS | Property Management System | 자산 운영, 입주민, 재무, 시설 |
| PPS | Product Planning System | 상품기획, 상품 구조, 가격·계약 조건, 운영 패키지 |
| CMS | Contents / Customer Management System | 고객 접점, 채널, 콘텐츠, 마케팅 |
| HMS | Homes Management System | 사내 운영, 회의, 지식, 권한 |

L1은 조직도와 1:1로 맞추기 위한 레이어가 아니라 업무를 수행 가능한 시스템 단위로 나눈 것이다.

### L2. Agents

L2는 각 system 내 대표 역할을 agent로 정의한 레이어다.

예:

- IMS의 검토 agent
- IMS의 딜 소싱 agent
- BMS의 계약 agent
- PMS의 재무 agent
- PPS의 상품기획 agent
- HMS의 회의 agent
- CMS의 채널 관리 agent

L2 agent는 하나의 기능 버튼이 아니라, 특정 업무 책임을 가진 역할 단위다.

### L3. Sub-agents

L3는 L2 agent를 실제 실행 가능한 세부 업무 단위로 나눈 레이어다.

예:

- 조율 agent 안의 투자자 보고 sub-agent
- 채널 관리 agent 안의 홈페이지 sub-agent
- 마케팅 agent 안의 콘텐츠 배포 sub-agent
- 계약 agent 안의 특약 검토 sub-agent

L3는 구현 단위에 가장 가깝다. 다만 L3부터 만들면 기능 목록이 흩어지기 쉽기 때문에, 항상 L1 system과 L2 agent 경계가 먼저 정의되어야 한다.

## 4. System별 agent 초안

### BMS — 중개

`Brokerage Management System`

BMS는 중개업을 다루는 system으로 중개사를 돕고 더 많은 계약을 체결할 수 있도록 지원하는 것이 본질이다.

BMS의 핵심 중개 업무는 `광고 -> 접수 -> 상담(자료 준비) -> 계약 -> 사후관리(CRM)`의 시간순 workflow를 따른다. 다만, IMS처럼 단일 파이프라인으로 끝나지 않고 본부 관제나 가맹점 지원 같은 병렬 지원 task가 함께 섞여 있다는 점이 특징이다.

주요 L2 agent:

| Agent | 역할 | L3 후보 |
|---|---|---|
| 광고 agent | 채널별 광고 운영과 성과 반영 | 채널 최적화, 이미지 정리, 성과 feedback |
| 접수 agent | 다채널 문의 접수와 배정 | 통화/채널톡/카카오/메일 통합, 진성도 scoring, 매칭 |
| 자료 준비 agent | 매물·상담·법률·규제 자료 준비 | 매물 검색, 상담자료 정리, 법률 가드레일, macro 참고 |
| 계약 agent | 계약 단계 관리와 리스크 점검 | 단계 tracking, 법정 의무 reminder, 특약 risk scoring, OCR |
| CRM agent | 고객 lifecycle 관리 | 신호 분류, persona dataset, 재접촉 시점 예측 |
| 가맹점 지원 agent | 가맹점 운영 지원 | 온보딩, 실패 통화 패턴, best practice 공유 |
| 본부 운영 agent | 본부 관제와 정책 준수 | 퍼포먼스 대시보드, 이상 거래 탐지, 브랜드 risk |

### IMS — 투자

`Investment Management System`

IMS는 투자개발본부 업무를 다루는 system이다. 기존 AMS는 별도 독립 system이 아니라 IMS 하위의 자산 발굴·검토 기능으로 흡수한다.

```text
소싱 -> 검토 -> 조율 -> 구조화
```

주요 L2 agent:

| Agent | 역할 | L3 후보 |
|---|---|---|
| 딜 소싱 agent | 유입 매물 수집, 정리, 1차 후보화 | 채널별 수집, 비정형 매물 정리, 중복 후보 병합 |
| 검토 agent | 사업성 검토 질문에 답하고 근거를 정리 | 개략 검토, valuation, 리스크 신호, 중단 사유 정형화 |
| 조율 agent | 투자자·매도인·내부 조율 자료 준비 | 투자자 보고, 공유자료 패키징, 일정/증빙 체크 |
| 구조화 agent | Deal 구조와 Plan A/B/C 비교 | 플랜 비교, 전환 신호 감지, 구조별 체크리스트 |

### PMS — 자산·운영

`Property Management System`

PMS는 잠재 고객 문의가 접수된 이후부터 재고 확인, 계약, 입주, 거주 경험, 시설 관리까지 이어지는 운영 흐름을 다루는 system이다.

운영 파트의 각 agent는 단순히 업무를 자동화하는 기능 묶음이 아니라, 담당 구간의 상태를 판단하고 다음 액션을 생성해 다음 역할로 넘기는 책임 단위다. PMS는 이렇게 축적된 운영 데이터를 통해 장기적으로 IMS와 BMS의 판단 정밀도를 높이는 입력원이 된다.

주요 L2 agent:

| Agent | 역할 | L3 후보 |
|---|---|---|
| 리드 관리 agent | 잠재 고객 문의를 상담·투어·계약 후보 리드로 전환 관리 | 문의 접수, 수요 조건 추출, 리드 상태 판단, 투어·상담 전환 |
| 재고 관리 agent | 추천·예약·계약 가능한 공간 단위 재고 관리 | 가용 공간 조회, 입주 가능성 판단, 공간 추천, 재고 상태 관리 |
| 계약 관리 agent | 예약 확정 이후 계약·입주 준비·청구·수납·변경 흐름 관리 | 계약 조건 관리, 계약 문서 처리, 청구·수납 관리, 계약 변경·연장·종료 관리 |
| 거주 경험 관리 agent | 입주 이후 요청·민원·만족도·재계약 신호 관리 | 입주민 문의, 요청·민원 조율, 생활 안내·경험 커뮤니케이션, 만족도·재계약 신호 감지 |
| 시설 관리 agent | 시설 이슈 대응과 예방 유지보수, 운영 안정성 관리 | 시설 이슈 분류, 유지보수 조율, 작업 상태 추적, 운영 리스크 반영 |

### PPS — 상품기획

`Product Planning System`

PPS는 홈즈가 제공하는 상품의 구조와 운영 조건을 기획하는 system이다. 고객 수요, 자산 특성, 운영 제약, 가격 조건, 계약 조건을 함께 보고 어떤 상품을 만들고 어떻게 운영할지 정의한다.

구체적인 L2 agent는 상품기획 담당자 초안이 전달된 뒤 확정한다.

주요 L2 agent:

| Agent | 역할 | L3 후보 |
|---|---|---|
| 작성 예정 | 상품기획 L2 agent 초안 수신 후 반영 | 작성 예정 |

### CMS — 채널·콘텐츠

`Contents / Customer Management System`

CMS는 고객 접점과 외부 채널을 담당한다.

주요 L2 agent:

| Agent | 역할 | L3 후보 |
|---|---|---|
| 채널 관리 agent | 홈페이지, SNS, 외부 채널 운영 | 홈페이지, SNS, 채널별 게시 관리 |
| 마케팅 agent | 콘텐츠 생성·배포·성과 분석 | 콘텐츠 생성, 배포, 성과 분석 |

### HMS — 사내시스템

`Homes Management System`

HMS는 사내 운영과 지식 관리를 담당한다.

주요 L2 agent:

| Agent | 역할 | L3 후보 |
|---|---|---|
| 회의 agent | 회의록, 액션 아이템, 리마인더 관리 | 회의 요약, 액션 추출, 후속 알림 |
| 챗봇 agent | 사내 지식 Q&A | 문서 검색, 담당자 찾기, 정책 질의응답 |

## 5. Agent 상세 문서 작성 기준

각 agent 상세 문서는 같은 기준으로 정리한다. 핵심은 "무슨 업무를 맡는가"보다 한 단계 더 들어가서, 어떤 상태를 판단하고 어떤 결과물을 만들어 다음 단계로 넘기는지까지 명확히 쓰는 것이다.

- 목적: 이 agent가 전체 업무 흐름에서 책임지는 구간을 한 문단으로 정의한다.
- 역할: 반복적으로 수행하는 주요 업무를 실제 담당 책임 중심으로 정리한다.
- 주요 판단: 사람 대신 또는 사람을 보조해 판단해야 하는 기준을 적는다.
- 주요 출력: 다음 단계에서 바로 쓸 수 있는 상태값, 추천 액션, 검토 결과물, 조율 필요 사항을 적는다.
- 서브에이전트: 상위 agent 안에서 필요한 핵심 처리 기능을 3-4개 정도의 실제 업무 단위로 나눈다.

너무 잘게 쪼개면 구현 목록처럼 보이므로, 서브에이전트는 기능 단위가 아니라 업무 단위로 적는 것이 원칙이다.

## 6. 구현

### 인스턴스별 구현 소요 추정

구현 단위는 L2 agent이다. 각 agent의 난이도와 예상 소요 시간을 추정하고, L1 system별로 소계를 집계한다.

난이도 기준: `S` 단순 보조 기능 / `M` 단일 workflow 또는 단일 데이터 흐름 / `L` 복수 데이터·도메인 판단 포함 / `XL` 전사 공통 기반 또는 cross-system orchestration

#### BMS — 중개

| L2 Agent | 난이도 | 예상 소요 | 비고 |
|---|---|---|---|
| 광고 agent | M | 4주 | 채널별 노출 룰과 사람 검수 기준 필요 |
| 접수 agent | M | 6주 | 통화/채널톡/카카오/메일 통합과 동의 설계 필요 |
| 자료 준비 agent | L | 8주 | 매물 검색만 분리하면 M/4주, 법률·규제 자료까지 포함하면 L |
| 계약 agent | S | 2주 | 계약 schema와 법정 의무 reminder 기준 필요 |
| CRM agent | L | 8주 | persona dataset과 내부 고객 데이터 정합 필요 |
| 가맹점 지원 agent | M | 6주 | 온보딩 자료와 실패 통화 패턴 누적 필요 |
| 본부 운영 agent | M | 6주 | 가맹점 거래 데이터와 정책 준수 기준 필요 |
| **BMS 소계** | L | **8-12주** | 병렬 진행 기준. 전체 순차 구현이면 더 길어짐 |

## 7. 유지 가능성

이 구조가 6개월 뒤에도 유지되려면 홈즈 내부의 지속 가능성이 중요하다.

내부 지속 가능성의 근거:

- 이미 홈즈 안에는 운영 데이터, 검토 이력, 회의록, Slack, Notion, 문서 자산이 축적되고 있다.
- AX팀은 자동 회의록, 액션 추적, 리마인더, 검색/정리 보조 같은 작은 시드를 이미 운영해봤다.
- agent는 별도 세계를 새로 만드는 것이 아니라, 기존 업무 자산을 Mycroft와 L1 system 구조 안에 연결하는 방식으로 붙는다.

유지 가능성의 핵심:

- 사람이 전부 수기로 관리하는 두 번째 뇌를 만들지 않는다.
- agent가 만들고 사람이 검토한 결과가 다시 시스템에 남아야 한다.
- 각 agent는 산출물뿐 아니라 로그, 실패 사례, 수정 피드백을 남겨야 한다.
